# BannerlordCoopSpectator3 Agent Guide

Ключове правило: у звичайному режимі без мого явного `ок` після плану агент не має права нічого впроваджувати, навіть якщо йому здається, що план очевидний. Явно активований `Goal` (режим Цілі) є винятком і керується окремим розділом нижче.

# База знань

Канонічна база знань про проєкт зберігається в `docs/ai/`.

Перед роботою прочитай `docs/ai/README.md`, а потім лише ті документи з `docs/ai/`, які стосуються поточної задачі. Не завантажуй усю базу знань без потреби.

# Goal (режим Цілі)

Режим Цілі активний лише тоді, коли користувач явно створив або активував незавершену Ціль через механізм `Goal`, а не просто вжив слово «ціль» у звичайному запиті.

Коли активна Ціль існує, агент ОБОВ'ЯЗКОВО читає та виконує `docs/ai/GOAL_MODE.md`.

Правила `docs/ai/GOAL_MODE.md` замінюють лише ключове правило про обов'язкове `ок` і розділ `Звичайний режим роботи`. Усі інші правила цього `AGENTS.md` залишаються чинними.

# Звичайний режим роботи

Перед будь-якими змінами коду, файлів, білдів, git-операціями, branch-операціями, staging, commit, якщо тільки користувач не скаже інакше, агент ОБОВ'ЯЗКОВО:

- робить окремий план;
- пояснює, що саме хоче зробити;
- чому вважає це правильним;
- які файли і методи буде чіпати;
- які ризики бачить;
- і ЧЕКАЄ мого явного підтвердження (`ок`, `підтверджую`, `approve`).

Без явного підтвердження ЗАБОРОНЕНО:

- редагувати файли;
- запускати build;
- робити git add / commit / branch / checkout / switch;
- вносити apply_patch;
- міняти конфігурацію середовища.

# Виправлення помилок

Перед виправленням помилки ОБОВ'ЯЗКОВО перевіряй, чи не може вона трапитись у інших типах битв.

# Проведення досліджень

Кожне дослідження проводь на найнижчих рівнях.

При необхідності використовуй ilspycmd, windbg, IDA Free.

# Git-дисципліна

1. Не змішувати в одному commit:
   - новий фікс;
   - чужі локальні зміни;
   - форматні зміни;
   - line ending churn.
2. Якщо Git показує великий diff через LF/CRLF, агент має прямо сказати про це ДО коміту.
3. Якщо commit виходить noisy, агент має попередити про це заздалегідь, а не після факту.
4. Якщо потрібен checkpoint commit, агент має прямо називати його checkpoint, а не подавати як чистий production fix.

# Діагностика

1. Будь-яка нова діагностика в hot path має бути:
   - або вимкнена за замовчуванням;
   - або gated через explicit verbose mode.
2. Diagnostic code не повинен потрапляти в production runtime без окремого обґрунтування.
3. Якщо діагностичний код може зачіпати native/runtime-sensitive state, агент має вважати його потенційно небезпечним і окремо це позначати в плані.

# Навчальний блок

Агент додає блок `Навчальний блок` лише у фінальній відповіді користувачу.

У проміжних повідомленнях, status updates, commentary, plan acknowledgements і коротких технічних уточненнях `Навчальний блок` НЕ додається.

Під "фінальною відповіддю" мається на увазі лише завершальне повідомлення після виконання або після завершеного етапу роботи.

Якщо інше правило каже додавати `Навчальний блок` у кожній відповіді, це правило має пріоритет.

# Пояснення англомовних термінів

Якщо агент у відповіді використовує англомовний технічний термін, назву підсистеми, назву патерна, назву corridor/path/shell/bridge/profile/state machine або іншу англомовну фразу всередині українського тексту, він ЗОБОВ'ЯЗАНИЙ одразу дати коротке пояснення українською в дужках.

Формат обов'язковий:

- `term (коротке пояснення українською)`

Приклади:

- `root cause (коренева причина)`
- `exact snapshot (точний знімок стану)`
- `hero-class bridge (міст сумісності між campaign-героєм і MP-класом)`
- `pre-spawn contract resolver (логіка, яка перед створенням агента вирішує, який контракт spawn треба застосувати)`

Правило застосування:

- пояснення треба давати при кожній новій англомовній фразі, яка важлива для розуміння;
- якщо в одному списку йде кілька англомовних пунктів, кожен пункт має мати окреме українське пояснення;
- не залишати англомовні технічні фрази без пояснення, якщо вони не є очевидними для не-технічного читача;
- якщо термін повторюється багато разів у тій самій відповіді, дозволено після першого повного пояснення далі використовувати його без повтору, але лише якщо сенс уже однозначний.
